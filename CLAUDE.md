# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Minecraft 26.3 datapack (data pack format 121, `min_format`/`max_format` in `pack.mcmeta`) adding custom "dungeon loot" items, plus a companion resource pack in `texturepack/`. Functions are written in [MC-Build](https://mcbuild.dev/docs/) (`.mcb` / `.mcbt`, mc-build 4.2.0) and compiled into plain `.mcfunction` files.

## Build and run

- `npm i mc-build` installs the compiler (dependency in `package.json`); run `npx mcb build` in the repo root to compile `src/` into `data/`, or `npx mcb watch` to rebuild on change. `mcb.config.js` holds the compiler options. mc-build 4.x does not clean stale output, so delete the generated function folders before a rebuild after renaming or removing sources.
- `build.ps1` (PowerShell + 7-Zip) zips the datapack into `.build/<baseArchiveName>-<version>[+dev].zip`, then runs `texturepack/build.ps1` to zip the resource pack. `exclude.txt` keeps `src/`, `texturepack/`, scripts, and config out of the datapack zip.
- There are no automated tests. `python docs/tools/check_old_keys.py` flags pre-26.3 keys in the JSON under `data/`, `docs/tools/Scan.java` parses it with the game's own codecs, and `docs/tools/CmdCheck.java` parses the generated commands with the game's dispatcher (needs the 26.3 client jar and Java 25, see `docs/verifying-against-vanilla.md`). Verify behavior by loading the pack in a Minecraft 26.3 world.
- Version lives in two places that must be kept in sync: `config.json` (`mc.version`, used by templates and the zip name) and `pack.mcmeta` (`meta.version` and `meta.changelog`). `config.json` `mc.dev: true` enables dev-only code (e.g. re-enabling the `satyrn.fdl.loot.variant` trigger every tick via `IF (config.dev)`).

## Source vs. generated output

- `src/` is the source of truth for **functions**. `data/foxcraft_dungeon_loot/function`, `data/minecraft/tags/function/load.json` and `tick.json` are generated by `mcb` and gitignored. Never edit them.
- Everything else under `data/` (loot tables, predicates, advancements, item modifiers, function tags in `tags/function/`, `data/global`) and `texturepack/` is hand-written JSON and is committed.
- `src/foxcraft_dungeon_loot.mcb` defines the top-level `load`, `tick`, `uninstall`, and `update_scoreboards` functions. Config values are templated with `<%config.x%>`; mc-build 4.x does not read `config.json`, so each file using it starts with `import ./config.js` (relative path), which loads `config.json` `mc`. Do not use `<%config.x%>` on a `} else execute ... run {` line, 4.2.0 leaves it unevaluated there; write the literal value.
- `src/macros.mcbt` holds shared templates (`break_item`, `rng`), invoked by name with no keyword. Files opt in with `import ../macros.mcbt`. `rng` wraps `/random`. End every if/else chain with a plain `else run {`, 4.2.0 can run an outer `else` when a called chain has no final `else`.

## Architecture: event-bus via function tags

Core tick/load logic is deliberately decoupled from items. `load`/`tick`/`uninstall` call function tags such as `#foxcraft_dungeon_loot:on_load`, `on_tick`, `on_uninstall`, `on_fall`, `on_snowball_used`, `on_warped_fungus_used`, `on_spider_eye_eaten`, `on_block`. These are hand-maintained JSON lists in `data/foxcraft_dungeon_loot/tags/function/`.

- Each item has `src/foxcraft_dungeon_loot/items/<item>.mcb`; each `function x` inside compiles to `items/<item>/x`. Items implement whichever hooks they need (`on_load`, `on_tick`, `on_snowball_used`, ...).
- **Adding or removing an item hook means also adding/removing its `foxcraft_dungeon_loot:items/<item>/<hook>` entry in the matching tag JSON**, otherwise it never runs.
- `src/foxcraft_dungeon_loot/events.mcb` turns vanilla stats and predicates (fall distance, used snowball / warped fungus on a stick, ate spider eye, blocked with shield) into those events. Item-specific events are only dispatched to players matching `predicate/events/process_*` (e.g. holding an event-enabled item), which is how the pack stays cheap on slow CPUs. New events need an objective, a predicate, a dispatch in `events.mcb`, and a tag file.
- Items use scoreboards/tags prefixed `satyrn.fdl.*`. Periodic work uses self-rescheduling `schedule function ... Nt` clocks started from `on_load`.

## Items and loot

- Each custom item is identified by an integer `DungeonLootId` in its `custom_data` component, written by `minecraft:set_custom_data` with an SNBT string tag such as `"{DungeonLootId:87,DungeonItem:1b}"`. Always use the SNBT string form: a JSON compound turns small ints into bytes and never matches. `DungeonLootId` must be unique (master list is a Google Sheet linked in `README.md`). The model comes from the `item_model` component (set in `set_components`), not a `CustomModelData` number.
- Item definitions are loot tables in `data/foxcraft_dungeon_loot/loot_table/items/<rarity>/...` (common, uncommon, rare, epic, mythic), with per-rarity `*_grab_bag.json` tables. Variants (e.g. chainsaw diamond/netherite upgrade) are selected by setting the `satyrn.fdl.loot.variant` score before `loot give`, then resetting it.
- Each loot table keeps only its pools plus a root `"modifier": "foxcraft_dungeon_loot:<table path>"`; the name, lore, components and custom data chain lives in `item_modifier/<table path>.json`, so edit the item there. Other folders in `item_modifier/` are per-item modifiers run by `item modify` in `src/`. `advancement/items/` holds use-detection advancements. `advancement revoke @a from foxcraft_dungeon_loot:items` runs on load to reset them.
- `data/minecraft/loot_table` overrides vanilla tables to inject the loot.

## Trades

`src/foxcraft_dungeon_loot/trades*.mcb{,t}` and `trades/` implement custom Wandering Trader offers. A trade **index** is built into storage `foxcraft_dungeon_loot:trades` by spawning loot-table items in a force-loaded chunk of the End (264, 64, 264). It runs over multiple ticks (`wait_for_chunk` then `build`), and `scheduled_tick` only starts once it's populated. Recipes are appended in `trades/index.mcb` using the `set_*_from_loot` macros in `trades.mcbt`; the position in the index (the `Trade Index N` comments) matters because offers are selected by index.

## Scoreboards

`config.json` `scoreboardsVersion` is compared against `#version` in `satyrn.fdl.internal`. When a scoreboard objective is renamed or its type changes, bump it and add the removal to `update_scoreboards` in `src/foxcraft_dungeon_loot.mcb`. Every objective added in an `on_load` needs a matching removal in `on_uninstall`.

## Resource pack

`texturepack/` is a separate pack (own `pack.mcmeta`, format 97.1, built by `texturepack/build.ps1`) with models, textures, sounds, and post effects. An item picks its model through the `item_model` component, which names a definition in `assets/foxcraft_dungeon_loot/items/<name>.json`; the definition points at a model in `models/item/` and holds state switches such as the bow pull stages. Do not add `custom_model_data` overrides to vanilla item models, 26.3 ignores them. Music discs are vanilla discs with a `jukebox_playable` pointing at a `data/foxcraft_dungeon_loot/jukebox_song/<id>.json`; their loot tables are `loot_table/items/discs/<id>.json`, with `give_<id>` functions in `src/foxcraft_dungeon_loot/items/music_discs.mcb`. The Wolfgun and C418 audio under `sounds/records/` is gitignored and must be copied in by hand, see `README.md` for credits and licenses.
