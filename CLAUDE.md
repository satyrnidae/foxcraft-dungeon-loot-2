# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Minecraft 26.3 datapack (data pack format 121, `min_format`/`max_format` in `pack.mcmeta`) adding custom "dungeon loot" items, plus a companion resource pack in `texturepack/`. Functions are written in [MC-Build](https://mcbuild.dev/docs/) (`.mcb` / `.mcbt`, mc-build 4.2.0) and compiled into plain `.mcfunction` files.

## Build and run

- `npm i mc-build` installs the compiler (dependency in `package.json`); run `npx mcb build` in the repo root to compile `src/` into `data/`, or `npx mcb watch` to rebuild on change. `mcb.config.js` holds the compiler options. mc-build 4.x does not clean stale output, so delete the generated function folders before a rebuild after renaming or removing sources.
- `build.ps1` (PowerShell + 7-Zip) zips the datapack into `.build/<baseArchiveName>-<version>[+dev].zip`, then runs `texturepack/build.ps1` to zip the resource pack. `exclude.txt` keeps `src/`, `texturepack/`, scripts, and config out of the datapack zip.
- `node tests/run_all.mjs` builds the pack and runs everything in `tests/`: a `node:test` suite with one generated test per item and per item source file, including a check for pre-26.3 keys, and, when Java 25 is found, with the client jar taken from the launcher or downloaded from Mojang, `Harness.java` for vanilla behavior, `Scan.java` for data codecs, `CmdCheck.java` for generated commands and `PackLoad.java` for the datapack validation the game does on load, which catches tags naming removed ids and bare-list modifiers. See `tests/README.md` and `tests/verifying-against-vanilla.md`. The tests are static, so verify behavior by loading the pack in a Minecraft 26.3 world, using `docs/todo_manual_verification.md`.
- Version lives in two places that must be kept in sync: `config.json` `mc.version`, which templates and the zip name use, and `pack.mcmeta` `meta.version` and `meta.changelog`. `config.json` `mc.dev: true` enables dev-only code such as re-enabling the `satyrn.fdl.loot.variant` trigger every tick via `IF (config.dev)`.

## Source vs. generated output

- `src/` is the source of truth for **functions**. `data/foxcraft_dungeon_loot/function`, `data/minecraft/tags/function/load.json` and `tick.json` are generated by `mcb` and gitignored. Never edit them.
- Everything else under `data/` (loot tables, predicates, advancements, item modifiers, function tags in `tags/function/`, `data/global`) and `texturepack/` is hand-written JSON and is committed.
- `src/foxcraft_dungeon_loot.mcb` defines the top-level `load`, `tick`, `uninstall`, and `update_scoreboards` functions. Config values are templated with `<%config.x%>`; mc-build 4.x does not read `config.json`, so each file using it starts with `import ./config.js` (relative path), which loads `config.json` `mc`. Do not use `<%config.x%>` on a `} else execute ... run {` line, 4.2.0 leaves it unevaluated there; write the literal value.
- `src/macros.mcbt` holds shared templates (`break_item`, `rng`), invoked by name with no keyword. Files opt in with `import ../macros.mcbt`. `rng` wraps `/random`. End every if/else chain with a plain `else run {`, 4.2.0 can run an outer `else` when a called chain has no final `else`.

## Architecture: event-bus via function tags

Core tick/load logic is deliberately decoupled from items. `load`/`tick`/`uninstall` call function tags such as `#foxcraft_dungeon_loot:on_load`, `on_tick`, `on_uninstall`, `on_fall`, `on_snowball_used`, `on_warped_fungus_used`, `on_spider_eye_eaten`, `on_block`. These are hand-maintained JSON lists in `data/foxcraft_dungeon_loot/tags/function/`.

- Each item has `src/foxcraft_dungeon_loot/item/<rarity>/<item>.mcb`, mirroring `loot_table/item`; each `function x` inside compiles to `item/<rarity>/<item>/x`. The copper horn and the discs are `item/special/copper_horn/main.mcb` and `item/special/music_disc/main.mcb`. Items implement whichever hooks they need (`on_load`, `on_tick`, `on_snowball_used`, ...).
- **Adding or removing an item hook means also adding/removing its `foxcraft_dungeon_loot:item/<rarity>/<item>/<hook>` entry in the matching tag JSON**, otherwise it never runs.
- `src/foxcraft_dungeon_loot/event.mcb` turns vanilla stats and predicates such as fall distance, a used snowball or warped fungus on a stick, an eaten spider eye and a shield block into those events. Item-specific events are only dispatched to players matching `predicate/event/process_*`, for example holding an event-enabled item, which is how the pack stays cheap on slow CPUs. New events need an objective, a predicate, a dispatch in `event.mcb`, and a tag file.
- Items use scoreboards/tags prefixed `satyrn.fdl.*`. Periodic work uses self-rescheduling `schedule function ... Nt` clocks started from `on_load`.

## Items and loot

- Each custom item is identified by an integer `DungeonLootId` in its `custom_data` component, written by `minecraft:set_custom_data` with an SNBT string tag such as `"{DungeonLootId:87,DungeonItem:1b}"`. Always use the SNBT string form: a JSON compound turns small ints into bytes and never matches. `DungeonLootId` must be unique (master list is a Google Sheet linked in `README.md`). The model comes from the `item_model` component (set in `set_components`), not a `CustomModelData` number.
- Item loot tables are in `data/foxcraft_dungeon_loot/loot_table/item/<rarity>/<item>.json` (common, uncommon, rare, epic, mythic), with the per-rarity `<rarity>_grab_bag.json` beside them. Discs and copper horns are in `item/special/music_disc/` and `item/special/copper_horn/`, named like their `item_modifier/special/` folders. Pickers and pools for random drops are in `item/random_loot/`, which holds the groups `armor`, `book`, `coin`, `player_head`, `potion`, `tool`, `grab_bag` and `advancement`, the `single_*` pickers and the per-rarity pools. Loot for entities is in `loot_table/entity/`. One file per item. An item with extra loot tables, like the Hammer of Sol, gets a folder with its main table in `<item>/drop.json` and the others beside it, such as `expiry.json`; the item is still named by the folder. Variants (e.g. chainsaw diamond/netherite upgrade) are selected by setting the `satyrn.fdl.loot.variant` score before `loot give`, then resetting it.
- Each loot table keeps only its pools plus a root `"modifier"` pointing at `foxcraft_dungeon_loot:<rarity>/<item>/define`, a file in `item_modifier/<rarity>/<item>/define.json`. The name, lore, components and custom data chain lives there, so edit the item in that file. Every item modifier file must be a single function object, the registry rejects a bare JSON list, so a chain of functions is wrapped as `{"type": "minecraft:sequence", "functions": [...]}`. Keep lore lines within the width of 44 average characters, 226 pixels in the default font, `scripts/lore.js`, one lore entry per line; a list of components counts as one line. A test in `integrity.test.mjs` fails the run for over-width lines on lines you changed against HEAD, staged or not. Old over-width lines are reported as todo subtests named `path:line: width "text"` so they can be opened; they never fail the run. Another test applies each pool entry's modifiers, the pool's and the table's root modifier in order and fails on a repeated lore line of 25 or more characters, as when a base define inserts a blurb a tier file already wrote. The same folder holds the item's other modifiers, such as the per-tier ones of the Tithe to Uthiir (`netherite.json`, `diamond.json`, `iron.json`, `copper.json`) that each pool entry of its loot table points at, such as `on_hit.json` or the `damage_*.json` ones that `item modify` runs from `src/`. Discs live in `item_modifier/special/music_disc/<disc>/`, named `<artist>_<title>` without the `music_disc_` prefix, and copper horns in `item_modifier/special/copper_horn/<song>/`, with the horn's `bass.json`, `harmony.json` and `melody.json` swap modifiers beside `define.json`. Modifiers for random loot such as heads, potions, coins, armor, books and tools live in `item_modifier/random_loot/<group>/`, and `item_modifier/remove.json` is the shared break step. `advancement/item/` holds use-detection advancements. `advancement revoke @a from foxcraft_dungeon_loot:item` runs on load to reset them.
- `data/minecraft/loot_table` overrides vanilla tables to inject the loot.

Every item source file defines `function give_<item>` and, for tiered items, `give_<item>_<tier>`, which set `satyrn.fdl.loot.variant` around the `loot give`. Items without hooks have a source file with only give functions. `src/foxcraft_dungeon_loot/give.js` scans the item sources for `function give_*` at build time, and `give.mcb` adds a trigger objective for each give function that is not a tier variant. The triggers exist only when `mc.dev` is true and work for any player. For a plain item the trigger value is the amount given, capped at 256. For an item with tiers it is the tier from the lowest, so `/trigger give_longsword set 3` gives the netherite one, because those items do not stack; `give.js` orders the tiers leather, chainmail, copper, iron, diamond, netherite and takes the base function's tier from the loot table's default pool, and the tier variants get no trigger of their own. Each pack enchantment also gets `give_<name>_book`, whose value is the level of the enchanted book it gives, up to the enchantment's own `max_level`; a release build adds none, and the functions stay for `/function`. A new give function needs no list entry.

## Enchantments

The history of the Tithe to Uthiir conversion from item-only to item and enchantment activation is in `docs/tithe-to-uthiir-enchantments.md`.

Custom enchantments are data-driven in `data/foxcraft_dungeon_loot/enchantment/`, ids like `foxcraft_dungeon_loot:aura_of_uthiir`. The Tithe to Uthiir is the proof of concept with `aura_of_uthiir`, `haemolymph_sacrifice` and `balm_of_the_spider_god`. They are not tied to an item, they work on any sword that has them, and the Tithe tiers only set them in `item_modifier/epic/tithe_to_uthiir/<tier>.json`. Uthiir's Grasp is not an enchantment but an intrinsic of the Tithe itself, found by its `DungeonLootId` in `predicate/item/epic/tithe_to_uthiir/killed_with`: the vanilla `spider`, `cave_spider` and `silverfish` loot tables in `data/minecraft/loot_table/entities/` have an extra pool that calls `loot_table/entity/uthiirs_grasp`, which gives the Grasp of Uthiir on 1 in 10 kills made with the sword. None of the enchantments is in an enchantment tag, so they never roll in an enchanting table, loot or trade; a test keeps it that way.

Their functions live in `src/foxcraft_dungeon_loot/enchantment/<name>.mcb` and compile to `enchantment/<name>/<function>`. Aura and Hæmolymph have a `post_attack` effect each: Aura runs `enchantment/aura_of_uthiir/post_attack` as the struck arthropod, and Hæmolymph runs `enchantment/haemolymph_sacrifice/on_killed_arthropod` as the attacker when the arthropod's `Health` is 0, a lethal hit. Balm has no hook and is run by the spider eye event tag. The level effects are chosen by predicates in `predicate/enchantment/<name>/`, `level_<n>`, which check only the enchantment in the main hand, or either hand for Balm. Balm's level picks the Strength, I to III for 10 seconds and IV for 30 seconds of Strength III. `Scan.java` swaps pack enchantment ids for vanilla stand-ins because the vanilla registry cannot take them.

## Books

Written book loot is generated from markdown in `src/books/<locale>/<id>.md` by `scripts/book_loot_gen.js`, which `mcb build` runs through `src/foxcraft_dungeon_loot/books.js`. It writes `item_modifier/random_loot/book/<id>.json`, `loot_table/item/random_loot/book/<id>.json` and the `texturepack/assets/foxcraft_dungeon_loot/lang/` files, so edit the markdown and never those outputs. The modifiers and loot tables are gitignored and made by the build, which also deletes any it has no source for; the lang files are committed. Format and layout are in `scripts/README.md`.

## Trades

`src/foxcraft_dungeon_loot/trading/` implements custom Wandering Trader offers. A trade **index** is built into storage `foxcraft_dungeon_loot:trades` by spawning loot-table items in a force-loaded chunk of the End (264, 64, 264). It runs over multiple ticks (`wait_for_chunk` then `build`), and `scheduled_tick` only starts once it's populated. Recipes are appended in `trading/index.mcb` using the `set_*_from_loot` macros in `trading/template.mcbt`; the position in the index (the `Trade Index N` comments) matters because offers are selected by index. 26.3 only saves Offers a trader already has, and vanilla generates its own on the first right-click, so the recipes are staged in the trader's body slot item (`StagedTrades`) and merged into `Offers.Recipes` by the `trading/on_interact` advancement after that first click, which also closes the screen by lifting the trader out of range for a tick. Offers are added in sections (heads, horns, grab bags, dungeon loot, endgame, exchange, discs), each with a count of random distinct trades picked from its index range. Disc trades are index 98 to 170, priced 2 to 10 gold coins.

## Scoreboards

`config.json` `scoreboardsVersion` is compared against `#version` in `satyrn.fdl.internal`. When a scoreboard objective is renamed or its type changes, bump it and add the removal to `update_scoreboards` in `src/foxcraft_dungeon_loot.mcb`. Every objective added in an `on_load` needs a matching removal in `on_uninstall`.

## Resource pack

`texturepack/` is a separate pack (own `pack.mcmeta`, format 97.1, built by `texturepack/build.ps1`) with models, textures, sounds, and post effects. An item picks its model through the `item_model` component, which names a definition in `assets/foxcraft_dungeon_loot/items/<group>/<name>.json`, grouped by rarity, `special/music_disc`, `special/copper_horn` or `random_loot/coin`; the definition points at a model in `models/item/` and holds state switches such as the bow pull stages. Do not add `custom_model_data` overrides to vanilla item models, 26.3 ignores them. Music discs are vanilla discs with a `jukebox_playable` pointing at a `data/foxcraft_dungeon_loot/jukebox_song/<id>.json`; their loot tables are `loot_table/item/special/music_disc/<artist>_<title>.json`, with `give_<id>` functions in `src/foxcraft_dungeon_loot/items/music_discs.mcb`. The Wolfgun and C418 audio under `sounds/records/` is gitignored and must be copied in by hand, see `README.md` for credits and licenses.
